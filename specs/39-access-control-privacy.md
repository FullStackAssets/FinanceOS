# FinanceOS — Section 39: Access control & privacy (items 761–780)

Builder spec for the FinanceOS Retool app (App 11). Single-user personal app: privacy means the user's data stays the user's. No multi-user roles, no sharing, no recovery-owner workflows are specified in this section — items 763–768 are written as deliberate non-implementation guard specs that assert and verify the single-user model.

## Tables touched

- accounts: id (pk), name (text), type (text), institution (text), balance (number), updated_at (timestamp), is_sample (bool), profile_id (fk → profiles, added item 777), hidden_from_overview (bool, added item 776)
- transactions: id (pk), account_id (fk), date (date), description (text), category (text), amount (number), is_sample (bool), profile_id (fk → profiles, added item 777)
- budgets: id (pk), category (text), month (text), limit_amount (number), profile_id (fk → profiles, added item 777)
- goals: id (pk), goal_name (text), target (number), saved (number), deadline (date), profile_id (fk → profiles, added item 777)

### New tables

- **profiles**: id (pk, uuid), name (text: e.g. "Personal", "Side business"), created_at (timestamp). One row per book of the same user; NOT user accounts.
- **app_security**: setting_key (pk, text), setting_value (text), updated_at (timestamp). Keys: `lock_enabled`, `pin_hash` (salted bcrypt), `lock_timeout_seconds`, `private_mode`, `retention_years`, `screenshot_mask`, `ai_consent_default`. Single-user device/app settings only.
- **data_purge_jobs**: id (pk), run_at (timestamp), cutoff_date (date), rows_purged (number), status (text: Completed / Failed). Log of retention purges.
- **delete_requests**: id (pk), requested_at (timestamp), typed_phrase (text), status (text: PendingRecovery / Purged / Cancelled), purge_at (timestamp). 30-day recovery window bookkeeping (item 773).

## Shared cross-cutting rules

- Every screen shows the persistent banner "Manual tracking — no bank connection yet."
- Sample rows carry `is_sample=true` + SAMPLE badge; when the sample toggle hides them they are excluded from totals.
- Nothing ever presents as a live bank feed.
- Retool is the only backend; no third-party analytics receives financial values (item 770).
- Financial figures are never sent to AI features without explicit per-use consent (item 775).

---

### 761. Add app-level PIN or biometric lock with a user-set fallback.

Components: Modal `lockModal` (full-screen, no dismiss) with Password input `pinInput`, button `unlockBtn`; Settings switch `lockEnabled`, button `setPinBtn`; on iPhone, Retool mobile `biometric` JS API call wrapped in try/catch. Data: `getSecuritySetting` query (Retool DB SELECT from app_security by setting_key); `setPin` JS query hashing PIN with bcrypt and upserting `pin_hash` + `lock_enabled`; `checkPin` transformer comparing input to stored hash; `lockNow` JS setting `localStorage.financeos_locked=true`. Logic notes: biometric is primary when available, PIN is always the fallback; lock engages on app open when `lock_enabled=true`; three failed PIN attempts impose a 30s cooldown. Acceptance: (1) enabling lock forces PIN setup before the toggle sticks; (2) reopening the app with lock enabled shows lockModal before any amount renders; (3) correct PIN unlocks, wrong PIN shows cooldown after 3 failures; (4) lockModal cannot be dismissed by backdrop click or Escape.

### 762. Support a private mode that hides amounts until tapped.

Components: Settings switch `privateMode`; Text components showing amounts gain `masked` state; on tap, amount reveals for 5s then re-masks. Data: `getSecuritySetting('private_mode')` drives a global `appVars.privateMode`; transformer `fmtAmount(amount)` returns "••••" when private mode is on and the row is not in `appVars.revealedIds`. Logic notes: masking is render-only — underlying values never change; revealed IDs expire via `setTimeout` and are cleared on screen change; private mode persists across sessions via app_security. Acceptance: (1) with private mode on, every currency figure on Overview, Accounts, and Transactions renders as "••••"; (2) tapping a masked amount reveals only that figure for 5s; (3) navigating away re-masks all revealed figures; (4) toggling private mode off restores all figures immediately.

### 763. Add household sharing: invite a partner with viewer or editor roles.

NOT IMPLEMENTED BY DESIGN — single-user app. Components: none built; the Settings screen contains no invite, member, or role UI by explicit design. Data: no members table is created; no role column exists on any table; the privacy dashboard (item 774) reads a static `sharingStatus` object `{enabled:false, members:[]}` to truthfully report "no one else has access." Logic notes: this spec documents the deliberate exclusion — FinanceOS is one person's books, so there is no invite flow, no role model, and no shared-session surface to secure; any future sharing request is a new product decision, not a hidden feature. Acceptance: (1) no "invite", "member", "role", or "share" control exists anywhere in the app; (2) the privacy dashboard shows sharing status "Off — single user"; (3) a code/grep review finds no member or role fields on financial tables; (4) the audit log contains no member-attribution fields.

### 764. Scope editor permissions per section (e.g., can add transactions, can't delete accounts).

NOT IMPLEMENTED BY DESIGN — single user, no roles to scope. Components: no permission matrix UI; destructive actions (delete account, purge data) are guarded instead by typed-confirmation modals that only the device owner can complete. Data: no permissions table; `deleteAccount` and `purgeData` queries check `localStorage.financeos_locked===false` (app is unlocked by owner) and require the typed confirmation phrase before executing. Logic notes: permission scoping presupposes multiple actors; with one actor the equivalent protection is friction on destructive acts (typed confirmation) plus the app lock (item 761); this spec pins that equivalence so a future reviewer does not re-add a role model by accident. Acceptance: (1) no per-section permission UI exists; (2) every destructive action requires a typed confirmation phrase; (3) destructive queries refuse to run while the app lock is engaged; (4) help text states "There is one user: you. No roles to configure."

### 765. Show a "shared with" list per record type in settings.

NOT IMPLEMENTED BY DESIGN — nothing is shared with anyone. Components: the privacy dashboard (item 774) includes a "Shared with" card that statically renders "No one — this app is single-user." Data: no shared_with table; the card reads the same static `sharingStatus` object as item 763 and lists each record type (accounts, transactions, budgets, goals, attachments) with access "Only you." Logic notes: this satisfies the item's information goal (a user can verify sharing status) without building sharing; if sharing ever ships, this card becomes dynamic and this spec is superseded. Acceptance: (1) Settings → Privacy shows a "Shared with" card; (2) the card lists all record types with "Only you" for each; (3) no invite or add-member control appears on the card; (4) the card text matches the guard language used in items 763–768.

### 766. Allow revoking a household member's access instantly.

NOT IMPLEMENTED BY DESIGN — there are no members to revoke. Components: no revoke buttons; the closest real feature is the app lock (item 761) plus PIN change, which together cut off anyone who had physical access to the device. Data: `changePin` query upserts a new `pin_hash` and sets `localStorage.financeos_locked=true` immediately, forcing re-authentication on next open; `revokeSessions` JS clears all `localStorage` keys prefixed `financeos_`. Logic notes: the threat model this item implies (an ex-partner with access) is addressed for a single-user app by credential rotation and device-level lock, not member management; this spec documents that equivalence. Acceptance: (1) changing the PIN immediately invalidates the old PIN; (2) a "Sign out everywhere / lock now" button re-locks the app instantly; (3) no member list or revoke control exists; (4) help text explains the PIN-change path for lost-device situations.

### 767. Display per-member activity in the audit log.

NOT IMPLEMENTED BY DESIGN — one actor, so the audit log attributes every entry to the owner. Components: the audit log screen (section 38) shows an "Actor" column that always reads "You (device owner)". Data: no member_id column on audit entries; the log's `actor` field is a constant string, not a foreign key, which makes multi-actor attribution structurally impossible without a schema change. Logic notes: keeping actor constant-by-design prevents a future half-built sharing feature from silently producing unattributed entries; per-member activity becomes meaningful only if sharing is ever deliberately added. Acceptance: (1) every audit entry's actor reads "You (device owner)"; (2) no member or user selector exists on the audit screen; (3) schema review confirms no actor/member foreign keys; (4) exporting the audit log shows the same constant actor on all rows.

### 768. Add a read-only "accountant view" share link with expiry.

NOT IMPLEMENTED BY DESIGN — no share links are generated. Components: no link-generation UI; the equivalent owner-controlled export is the manual CSV/PDF export (section 25) and the JSON portability export (item 772), which the user sends themselves through their own channels. Data: no share_tokens table; no URL in the app grants read access to financial data; Retool's own app permissions remain the sole access gate and stay owner-only. Logic notes: a share link is a bearer credential for financial data — for a single-user app the safer primitive is an explicit file export the owner chooses to send; this spec forbids token-based read URLs. Acceptance: (1) no "share link", "accountant view", or token-generation control exists; (2) no URL in the app exposes financial data without full app login; (3) the export screens are the documented path for sharing data with an accountant; (4) grep finds no token/expiry fields on any table.

### 769. Mask account institution names in screenshots via a privacy toggle.

Components: Settings switch `screenshotMask` bound to app_security key `screenshot_mask`; when on, all institution-name Text components render as "•••• Bank" and account names show only the user-set nickname. Data: transformer `fmtInstitution(name)` returns masked form when `appVars.screenshotMask` is true; the toggle upserts the setting. Logic notes: masking applies to institution + account number fragments only, never to balances or user-entered names (the user may want those visible); the banner and SAMPLE badges stay visible so a screenshot never misrepresents data as a live feed. Acceptance: (1) enabling the toggle masks every institution name across Overview, Accounts, and exports preview; (2) balances and nicknames remain readable; (3) the manual-tracking banner still renders in masked mode; (4) the setting persists across sessions.

### 770. Store all data locally to the Retool backend with no third-party analytics on financial values.

Components: none visible — this is an architecture guard; a "Data & privacy" settings card documents it. Data: all queries target Retool Database resources only; an `outboundAudit` JS transformer lists every REST/API resource in the app and asserts none is an analytics endpoint; no Segment/Mixpanel/GA resource exists in the app. Logic notes: Retool's own platform telemetry is outside the builder's control and is disclosed in the help-center privacy doc (item 780); the guard covers builder-added analytics only; any new REST resource added later must pass the `outboundAudit` check. Acceptance: (1) the app's resource list contains zero analytics or tracking resources; (2) no query sends account/transaction/budget/goal fields to a non-Retool host; (3) the settings card states "Your numbers never leave Retool's backend for analytics"; (4) adding a new REST resource triggers a review checklist item.

### 771. Add a data-retention setting: auto-purge transactions older than N years.

Components: Settings number input `retentionYears` (1–10, default 7) + "Purge now" button + last-purge summary text. Data: `getSecuritySetting('retention_years')`; `purgeOldTransactions` SQL: DELETE FROM transactions WHERE date < CURRENT_DATE - (retention_years || ' years')::interval AND is_sample=false; insert into data_purge_jobs with rows_purged = affected count; sample rows are never purged. Logic notes: purge runs only on explicit "Purge now" tap or a scheduled Retool workflow — never silently on open; a confirmation modal states the row count and that the action is irreversible after the recovery window does not apply here (item 773's window is only for full-delete requests). Acceptance: (1) setting N years persists and displays the last purge date + rows purged; (2) purge deletes only non-sample transactions older than the cutoff; (3) accounts, budgets, and goals are untouched; (4) each purge writes a data_purge_jobs row with an accurate count.

### 772. Provide a full data export (JSON) for portability.

Components: Settings button `exportJsonBtn`; on tap, generates and downloads `financeos-export-YYYY-MM-DD.json`. Data: JS query `buildJsonExport` runs SELECTs over accounts, transactions, budgets, goals, profiles, and app_security (excluding `pin_hash`), assembles one JSON object with schema version + export date, and triggers download via `utils.downloadFile`. Logic notes: export includes the manual-tracking banner text and an `is_sample` flag on every row so re-imported data stays honest; the file never includes the PIN hash or biometric material; export is owner-initiated only. Acceptance: (1) the JSON contains all six data sets with a top-level `exported_at` and `schema_version`; (2) no `pin_hash` or credential material appears in the file; (3) every financial row carries its `is_sample` flag; (4) the downloaded file opens as valid JSON in a text editor.

### 773. Add a "delete my data" flow with typed confirmation and a 30-day recovery window.

Components: Settings danger-zone button `deleteMyDataBtn` → modal requiring the typed phrase "DELETE ALL MY DATA" → schedules purge; a "Cancel deletion" button visible during the window. Data: `requestDelete` inserts into delete_requests with purge_at = now()+30 days and sets a `deletion_pending` flag; a scheduled Retool workflow runs daily: for requests past purge_at with status PendingRecovery, hard-deletes all rows across financial tables and marks Purged; `cancelDelete` sets status Cancelled. Logic notes: during the window the app shows a persistent "Deletion scheduled — undo" banner and all screens become read-only; this is a user-initiated flow, not an agent action. Acceptance: (1) deletion requires typing the exact phrase — the button stays disabled otherwise; (2) during the 30 days the app is read-only with an undo banner; (3) cancel restores full access with zero data loss; (4) after purge_at the workflow removes all financial rows and logs the purge.

### 774. Show a privacy dashboard: what data exists, where, and sharing status.

Components: Settings → "Privacy dashboard" screen with Stat cards: row counts per table (accounts, transactions, budgets, goals, attachments), storage location card ("Retool Database — US"), sharing card ("Off — single user"), AI card ("Figures never sent to AI without per-use consent"). Data: `privacyCounts` query with COUNT(*) per table; static cards for location and sharing; the AI card reads app_security `ai_consent_default`. Logic notes: counts exclude nothing — sample rows are counted separately and labeled; the dashboard is read-only truth, not a control panel (controls live on their own settings rows). Acceptance: (1) every card shows a live count matching the tables; (2) sample vs real rows are labeled separately; (3) sharing card reads "Off — single user" with a link to the help-center privacy doc; (4) no control on this screen mutates data.

### 775. Never transmit financial figures to AI features without explicit per-use consent.

Components: any AI-feature button (categorization, insights) opens a consent modal first: "Send these figures to the AI? [list of fields] Allow once / Don't allow". Data: `aiConsentModal` JS holds the exact payload preview; the AI query only executes after "Allow once"; `app_security.ai_consent_default` can preset "always ask" (default) — there is no "always allow" preset. Logic notes: consent is per invocation, not per feature; the payload preview shows field names and row counts, never full dumps when a summary suffices; denying leaves the feature inert with no retry nag. Acceptance: (1) triggering any AI feature shows the consent modal before any network call; (2) the modal lists exactly which fields will be sent; (3) "Don't allow" cancels with zero transmission and no error toast; (4) no setting exists to blanket-approve AI transmission.

### 776. Add per-account visibility controls (hide an account from the overview).

Components: Accounts screen row action "Hide from overview" / "Show"; hidden accounts render dimmed with an eye-off icon. Data: `toggleAccountVisibility` UPDATEs accounts.hidden_from_overview; the Overview net-worth query becomes `SELECT SUM(balance) FROM accounts WHERE hidden_from_overview=false AND profile_id=current`; the Accounts screen itself still lists hidden accounts. Logic notes: hiding is display-only — transactions on hidden accounts still appear in Transactions and budgets; sample-toggle and hidden flags compose (hidden applies after the sample filter). Acceptance: (1) hiding an account removes its balance from the Overview net worth immediately; (2) the account remains visible and editable on the Accounts screen, marked hidden; (3) unhiding restores it to the Overview total; (4) hidden accounts' transactions still count in spending totals.

### 777. Support multiple profiles (e.g., personal vs side-business) with separate tables.

Components: top-bar Profile switcher dropdown (single user, multiple books); "Manage profiles" in Settings with add/rename (no delete while rows reference it). Data: profiles table; accounts/transactions/budgets/goals carry profile_id; a startup query sets `appVars.activeProfileId` (default: the "Personal" profile); every financial query filters `WHERE profile_id = {{appVars.activeProfileId}}`. Logic notes: profiles are data partitions for the same owner — NOT user accounts, no login switching, no per-profile permissions; net worth, budgets, and goals are always per-profile; sample data is seeded per profile. Acceptance: (1) switching profiles changes every figure on every screen with no cross-profile leakage; (2) adding a transaction files it under the active profile only; (3) no sign-in, invite, or role UI exists on the profile switcher; (4) deleting the last profile is blocked while financial rows reference it.

### 778. Display a lock-screen widget showing only the manual-tracking banner, no amounts.

Components: when `localStorage.financeos_locked=true`, the app renders `lockedView`: the banner "Manual tracking — no bank connection yet.", a lock icon, and the PIN/biometric prompt — zero financial components mounted. Data: no financial query runs while locked; `appVars.locked` gates all data queries via "Run only when" conditions. Logic notes: this is the iOS widget analogue inside the Retool mobile app — the locked view must be the first paint, so queries are disabled-by-default and only enabled after unlock; screenshots of the locked state show nothing sensitive. Acceptance: (1) with lock enabled, cold-open first paint shows only banner + lock prompt; (2) no account/transaction query executes before successful unlock (verify in query history); (3) backgrounding the app re-engages the locked view per the timeout (item 779); (4) a screenshot of the locked view contains no amounts, names, or institutions.

### 779. Add session timeout that re-locks the app after inactivity.

Components: Settings select `lockTimeout` (1 / 5 / 15 / 30 min, default 5); invisible `activityTracker` JS. Data: `getSecuritySetting('lock_timeout_seconds')`; JS registers last-activity timestamps on pointer/key events and runs a 10s interval check: if now - lastActivity > timeout, set `localStorage.financeos_locked=true` and show `lockedView`. Logic notes: the PIN/biometric modal (item 761) counts as activity so it never times out mid-entry; timeout applies per device session and resets on unlock; backgrounding the tab counts as immediate inactivity. Acceptance: (1) with a 1-min timeout, idle 60s re-locks the app and shows the locked view; (2) any tap or keypress resets the idle clock; (3) changing the timeout takes effect without reopening the app; (4) the locked view appears without a page reload.

### 780. Document the privacy model in plain language in the help center.

Components: Help center article "Privacy: how your data is handled" (section 49's help system), linked from Settings → Privacy dashboard. Data: static article content covering: single-user (no sharing, no roles), Retool-only backend, no analytics on financial values, AI per-use consent, retention purge, JSON export, 30-day delete recovery, app lock. Logic notes: article is written at an 8th-grade reading level, no jargon without a plain-English gloss; it must be updated whenever items 761–779 change behavior — the article ends with a "Last updated" date the builder bumps per change. Acceptance: (1) the article exists and is reachable from both Help and the privacy dashboard; (2) it states the single-user model and the no-sharing items (763–768) in plain language; (3) it names where data lives and how to export/delete it; (4) a "Last updated" date is present and accurate.
